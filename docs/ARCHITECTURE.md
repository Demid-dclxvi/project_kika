# Устройство ядра

## Принципы

- **Всё на C++20.** Ядро — библиотека без интерфейса `kika_core`. Консольная программа, окно на Qt, тесты и будущие серверные расчёты работают с одним и тем же ядром.
- **Единицы:** мм, Н, МПа, мм³, °C. **Оси** — как у принтера: X, Y по столу, Z вверх по слоям.
- **Тензоры** — в нотации Фойгта `[11, 22, 33, 23, 13, 12]`, сдвиги инженерные (γ = 2ε), как в прототипе. Оси валика: 1 — вдоль нити, 2 — поперёк нити в слое, 3 — по Z.
- **Перенос со сверкой.** Каждый модуль прототипа переносится так, чтобы на тех же входах C++ и Python давали одинаковый результат. Отличия допускаются, только если они сознательные; все они перечислены ниже.
- **Минимум сторонних библиотек.** Ядро собирается одним компилятором без них: JSON (задания, итоги) — свой, `kika::json`, параметры командной строки разбираются вручную. Отчёт (`kika_report`, отдельно от ядра) сжимает данные через zlib и встраивает three.js. Чтение моделей (`kika_geometry`) распаковывает 3MF через zlib, XML разбирает сам. Свой слайсер (`kika_slicer`) строит контуры слоёв на Clipper2. Через vcpkg подключаются zlib, Clipper2 и Catch2 (только тесты). Дальше сторонние библиотеки — там, где своё писать неразумно: Qt (окно), OpenCascade (STEP).
- **Своя линейная алгебра.** Плотные матрицы 6×6, разреженные CSR, многосеточный решатель и сопряжённые градиенты написаны в ядре (`kika::linalg`), без Eigen и AMGCL: нужных операций немного, алгоритм решателя совпадает с прототипом шаг в шаг (это упрощает сверку), а ядро собирается и проверяется без сторонних библиотек.
- **Потоки.** Сборка матрицы, умножения разреженных матриц и разложение грубой задачи идут на всех ядрах (`kika::set_thread_count`, переменная окружения `KIKA_THREADS`). Работа делится так, что результат до последнего бита не зависит от числа потоков.
- **Лицензии.** Только те, что допускают закрытую продажу: MIT, BSD, Apache, MPL, Boost, LGPL с динамической линковкой. AGPL — никогда. Реестр — в [THIRD_PARTY.md](../THIRD_PARTY.md).
- **Сообщения пользователю** — по-русски. Идентификаторы в коде — по-английски, комментарии — по-русски.

## Поток данных

```
STL, 3MF ──► geometry::load_model ──► поворот, на стол ──► slicer::slice ──► свой G-code ─┐
                                                                                         ▼
G-code ─────────────────────────────────────────► gcode::parse ──► Toolpaths ──► воксели / сетка ──► поле материала
                                                                                                         │
отчёт ◄── запас прочности (Хоффман) ◄── напряжения ◄── МКЭ: K·u = f ◄──────────────────────────────────────┘
                                                          ▲
                                       нагрузки и закрепления
```

Модель всегда превращается в G-code своим слайсером, и дальше расчёт идёт тем же путём, что по G-code из чужого слайсера: прочность считается по тем нитям, которые принтер действительно положит. STEP добавится тем же путём (OpenCascade → треугольная сетка).

## Порядок переноса

1. Разбор G-code — готов.
2. Материалы и воксельная модель — готовы.
3. МКЭ и решатель — готовы: матрицы элементов, сетка, глобальная матрица и перемещения совпадают с прототипом.
4. Нагрузки и расчётные случаи, команда `kika run` — готовы. Консольная балка против аналитики, как в `prototype/tests/test_cantilever.py`: прогиб больше аналитического на 2–3 % (податливость заделки), запас посередине пролёта — в пределах 1 %. Задания кронштейнов и все виды нагрузок дают те же итоги, что прототип.
5. Отчёт: тот же HTML с three.js, что у прототипа, — смотреть результаты в браузере. Готов.
6. Окно вместо веб-приложения прототипа — готово.
7. Модели и свой слайсер — готовы для STL и 3MF; STEP — следующим шагом. Потом — тетраэдрическая сетка по модели.

## Отличия от прототипа

| Где | Прототип | C++ | Почему |
| --- | --- | --- | --- |
| Слова G-code без пробелов, `G1X10Y20E1` | `X10E1` читался как X = 10·10¹, экструзия терялась | X = 10, E = 1 | в числах G-code нет экспоненты |
| Строки с номером `N…` и контрольной суммой `*…` | строка пропускалась целиком | номер и сумма отбрасываются, команда выполняется | так G-code шлют по USB и пишут некоторые прошивки |
| Дуга с огромным радиусом | число точек не ограничено | не больше 100 000 точек на дугу | защита от испорченных файлов |
| Решатель для задач до 6000 неизвестных | прямой (SuperLU) | всегда многосеточный + сопряжённые градиенты; до 3000 неизвестных уровней нет, грубая задача решается Холецким за одну итерацию | один путь в коде, не нужен разреженный прямой решатель; ответ тот же с точностью невязки 10⁻⁷ |
| Начальный вектор оценки спектрального радиуса | `numpy.random.default_rng(0)` | свой генератор (splitmix64 + Бокс — Мюллер) | одинаков на всех платформах; влияет только на число итераций, не на ответ |
| Грубая матрица не раскладывается по Холецкому | псевдообратная матрица | сдвиг диагонали растёт 10⁻¹⁰ → 10⁻⁴ от наибольшего диагонального, затем сопряжённые градиенты | без разложения большой плотной матрицы по собственным числам |
| Грубая задача больше 4000 неизвестных | разреженный LU | сопряжённые градиенты с диагональным предобусловливанием до невязки 10⁻¹² | нет разреженного прямого решателя; бывает, только если огрубление застопорилось |
| Глобальная матрица жёсткости | точные нули из суммы элементов выбрасываются | портрет строится по соседству узлов, такие нули хранятся | на результат не влияет; сборка без сортировки, параллельно |
| Скалярные произведения и разложение Холецкого | одна сумма | четыре частичные суммы | быстрее; отличие — в последних знаках |
| Пустой список областей `"where": []` | закрепление ничего не держит, сила делится на ноль | ошибка «не задана область» | пустая область — почти наверняка ошибка в задании |
| Свой материал без `base` и без `name` | падение при выводе итогов | название «Свой материал» | |
| Фаза разреженного заполнения у вокселя с долей заполнения ровно 0,02 | зависит от соседей по пачке из 4000 элементов | считается всегда | порядок обработки не должен влиять на результат |
| Задания в YAML | читаются, если установлен pyyaml | только JSON | без лишней зависимости |
| Где сохраняется отчёт | в текущей папке | рядом с заданием | при перетаскивании на `kika.exe` текущая папка непредсказуема |
| Отчёт после перетаскивания задания на `kika.exe` | — | сразу открывается в браузере (`--open` — из командной строки) | |
| Подпись в отчёте | «fdmfea 0.1.1» | «kika 0.1.0» | |
| Файлы просмотрщика | читаются из папки `web/` рядом с программой | встроены в `kika.exe` при сборке (`cmake/EmbedFiles.cmake`) | программа — один файл |
| Поля решателя в итогах (`solver`) | `прямой` или `AMG+CG` | всегда `AMG+CG`, плюс время подготовки `setup_time` | см. строку о решателе выше |
| Точность решателя | 1e-7, не меняется | 1e-7, `kika run --tol` | для сверки с прототипом при строгой точности |
| Приложение | веб-страница и локальный сервер на Python (`server.py`), 3D на three.js | окно на Qt, свой 3D-вид на OpenGL, расчёт в фоновом потоке той же программы | не нужны браузер и Python |
| Убрать грани из выбора | Alt + щелчок | Alt или Ctrl + щелчок | Alt + щелчок в Linux обычно занят оконным менеджером |
| Сохранённое задание | `{"app": "fdmfea", "ui": …, "points": …, "job": …}` | формат `kika run`: поверхности — номерами граней (`"where": {"faces": […]}`), плюс `gcode` и `max_elems` | один формат для окна и `kika run`; файлы прототипа окно тоже открывает |
| Отчёт из приложения | скачивается из браузера | «Сохранить как…», затем открывается в браузере | |
| Деталь в 3D-виде окна | кубики воксельной сетки | нити — валики по отрезкам G-code; кубики — кнопкой «Сетка» | видно, как деталь напечатана; цвета полей те же (по элементу, через который идёт кусок нити) |

| G-code своего слайсера | — | слайсер в шапке — «Kika»; разбор узнаёт его по строке `; generated by Kika` | как у остальных слайсеров |

## Окно

Окно (`apps/gui`, программа `kika-gui`) — Qt 6 Widgets. Всё, что можно проверить без экрана, вынесено в `kika_app` (`src/app`, без Qt) и покрыто тестами: видимые грани с разрезом, цвета полей и легенда (`Scene`), выбор граней — плоская грань, стенка отверстия, кисть, луч из камеры (`Scene::pick`), перенос выбора на сетку другой детальности, перевод задания окна в JSON для расчёта и обратно (`job_model`). Окно только рисует и раскладывает виджеты.

- **3D-вид** (`viewer.cpp`) — `QOpenGLWidget`, шейдеры GLSL 1.10 (OpenGL 2): работает и на программном рендеринге (Mesa llvmpipe — `opengl32sw.dll` на Windows без драйвера). Освещение и камера — как в просмотрщике прототипа; легенда, подсказка под курсором и отметка слабого места рисуются `QPainter` поверх.
- **Без moc.** Сигналы подключаются лямбдами, `Q_OBJECT` нигде нет — сборке не нужны генераторы Qt.
- **Фоновая работа.** Построение сетки, расчёт и отчёт идут в `QThread`; ход расчёта и результат возвращаются в окно через очередь событий. При закрытии окна расчёт прерывается на ближайшем этапе.
- **Нити** (`app::Roads`). Каждый отрезок экструзии режется по границам ячеек расчётной сетки, и кусок красится цветом своего элемента — так нити показывают те же поля, что и кубики. Сечение валика — ромб из 4 вершин со сглаженными нормалями; соседние куски одного цвета делят кольца вершин. Разрез — по середине куска, деформация — трилинейно по перемещениям узлов ячейки.
- **Проверка без человека.** `kika-gui --example --run --field sf --screenshot окно.png` открывает пример, считает, переключает поле, сохраняет снимок окна и выходит (код 1, если были ошибки); есть `--section`, `--deform`, `--display`, `--tool`, `--pick`, `--rotate`, `--report`, `--save-job`, `--save-gcode`. В CI так проверяется окно на Linux (Xvfb) — пример по G-code и по модели 3MF с поворотом — и на Windows (программный OpenGL), снимки — в артефактах.
- **Qt подключается динамически** (LGPL-3.0): на Windows — отдельная конфигурация `win-gui-*` со средой выполнения C++ в DLL (`/MD`, триплет vcpkg `x64-windows-static-md`). Папку для пользователя собирает CI: `windeployqt`, среда выполнения Visual C++, примеры, лицензии (`packaging/windows`).

## Модели и свой слайсер

- **Чтение** (`kika_geometry`). STL — двоичный (узнаётся по размеру файла, даже если начинается со слова `solid`) и текстовый. 3MF — ZIP со сжатием deflate или без него, ZIP64; единицы (микроны…метры), матрицы преобразований, компоненты и ссылки на другие файлы модели (3MF Production), подставки (`type="support"`) и непечатаемые объекты пропускаются. После чтения совпадающие вершины сливаются, вывернутая наизнанку сетка переворачивается; незамкнутость — предупреждение. Из `.gcode.3mf` (Bambu, Orca) достаётся готовый G-code.
- **Нарезка** (`kika_slicer`). Сечение — посередине слоя; отрезки склеиваются в контуры по рёбрам сетки (точка на ребре считается всегда от меньшего номера вершины к большему, поэтому у соседних треугольников совпадает до бита), направление отрезка — по порядку вершин треугольника, так что отрезки нулевой длины не рвут контур. Контуры объединяются по правилу ненулевой обмотки — перекрывающиеся тела сливаются. Стенки — смещения контура внутрь; сплошные слои — где в пределах `top/bottom` слоёв над или под слоем нет материала; разреженное заполнение заходит на стенку на 15 % ширины линии; маленькие (< 15 мм²) участки разреженного заполнения печатаются сплошными. Шаг между валиками — `w − h·(1 − π/4)`, как у OrcaSlicer. Линии заполнения привязаны к общему началу координат — от слоя к слою они встают друг над другом.
- **G-code** — в стиле OrcaSlicer: `;LAYER_CHANGE`, `;Z:`, `;HEIGHT:`, `;TYPE:`, стартовый и финальный код принтера, настройки в конце. Экструзия относительная; после стартового кода всегда `G90`, `M83`, `G92 E0` — даже если стартовый код включает другое. Откат на перемещениях длиннее 2 мм.
- **Проверка.** Консольная балка, нарезанная своим слайсером, против аналитики: прогиб +2,0 % (по `mini_slicer` прототипа +2,1 %), запас посередине пролёта +1,1 % (+0,9 %). Объём пластика у куба и трубы при 100 % заполнении — в пределах 3–4 % от объёма модели. Уголок `examples/bracket_L.3mf` режется в шести положениях без разрывов контуров.
- **Поворот в окне.** Кнопки поворачивают деталь на 90°; после новой нарезки грани закреплений и нагрузок переносятся на новую сетку через точки на гранях (`app::rotate_job`), направления нагрузок, оси моментов, заданные перемещения и закреплённые оси поворачиваются вместе с деталью.

## Сверка с прототипом

`tools/compare_with_prototype.py` прогоняет примеры из `prototype/examples` и синтетические случаи из тестов прототипа через обе версии и сравнивает каждый отрезок (относительная точность 10⁻¹²) и все сведения о печати. В CI сверка идёт на Linux после тестов.

Расчёт (`kika run`) сверяется там же: задания обоих кронштейнов, задание со всеми видами нагрузок из `prototype/tests/test_all_loads.py` и консольная балка плашмя и стоя. Сравниваются итоги каждого случая (запас и его точка, вид разрушения, перемещения, реакции, предельная нагрузка, тексты предупреждений), воксельная модель (до 10⁻⁹) и поля по элементам: перемещения, запас, напряжения, вид разрушения. Оба решателя итерационные и сходятся до невязки 10⁻⁷; при такой точности случай с заданным перемещением расходится в шестом знаке, поэтому при сверке обе версии решают с невязкой 10⁻¹¹ — тогда все поля совпадают до точности float32, в которой их хранит прототип. Если наибольшее значение достигается в двух симметричных точках, точка может оказаться другой — скрипт это показывает, но не считает расхождением.

Там же сверяется HTML-отчёт: скрипт строит отчёт прототипом (`report_html`) по тому же расчёту и сравнивает распакованные данные 3D-просмотра (сетка, поля, выделенные грани, итоги) и весь видимый текст — шапку, карточки случаев, справку (кроме даты, времени расчёта и версии). Сам просмотрщик (`src/report/web`) — копия файлов прототипа без изменений; что отчёт открывается и 3D-вид работает, проверялось в Chromium.

Эталонные числа из этих сверок вошли в тесты (`tests/material`, `tests/voxel`, `tests/fem`, `tests/analysis`).
